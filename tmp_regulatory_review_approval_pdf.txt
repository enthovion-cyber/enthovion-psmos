================================================== PURPOSE
==================================================
This phase ensures important regulatory records are formally reviewed, approved, rejected, returned, or
signed before they are treated as current governance records.
It must answer:
• Which regulatory items need review?
• Which applicability decisions need approval?
• Which obligations need approval?
• Which compliance status decisions need approval?
• Which evidence verification decisions need review?
• Which audit mappings need verification approval?
• Which regulatory CAPA / action closure decisions need approval?
• Which review packages are pending, overdue, approved, rejected, returned, stale, or completed?
• Who submitted each item?
• Who reviewed it?
• Was e-signature required?
• Was e-signature completed?
• Which source records are locked after approval?
• Which approved records became stale because the source changed?
• Which approvals were conditional?
• Which conditions remain open?
• Which reviews are blocking compliance status, reports, or executive KPI readiness?
• Which review history is audit-ready?

================================================== ABSOLUTE RULES
==================================================
• No mock/static production data.
• No fake approvals.
• No fake signatures.
• No fake reviewer names.
• No fake compliance approval.
• Backend must be the source of truth.
• Frontend must never calculate final review status, approval status, validation readiness, stale status,
source lock status, e-sign status, or SLA status.
• Backend must enforce all permissions.
• Backend must enforce company/site/unit/area/equipment isolation.
• Backend must enforce RLS policies.
• Do not trust frontend IDs.
• Do not duplicate global Review & Approval if it exists.
• Do not duplicate Universal E-Signature if it exists.
• Use Review & Approval adapter.
• Use E-Signature adapter.
• Every review package must have a valid regulatory source record.
• Every review package must belong to a company.
• Site-scoped review packages must have site_id .
• Every review package must store immutable source snapshot.
• A source record change after submission must mark review package stale.
• Stale review packages cannot be approved unless refreshed/resubmitted.
• Self-approval must be blocked if setting requires separation of duties.
• Critical regulatory decisions must require elevated reviewer/e-signature if configured.
• Approval does not equal legal certification.
